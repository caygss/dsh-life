# 测试报告（模板文档）

> 本文档对应仓库 0.1.0。第 3–8 节的数字由 `tests/report.mjs` 跑出，可以复现：`node tests/report.mjs`。
> 其中 3.4 / 3.5 两节额外调用了一次真实 embedding 服务（2 个请求，见该节），7.2 节是从两台真实运行实例的库里做的聚合；
> 除这两处之外，整个过程不调用模型、不联网、不需要 key。

## 1. 这份报告测了什么、没测什么

| 测了 | 怎么测 |
|---|---|
| 记忆召回（本地 `hash-bigram-v1`，4 个维度） | 14 条合成记忆 + 28 个问题，看目标排在第几 |
| 记忆召回（真实 `Qwen3-Embedding-8B`，4096 维） | 同一套语料与问题，2 次真实 embedding 请求 |
| 五因子打分的量与比例 | 用真实 `DEFAULT_WEIGHTS` 算各因子贡献 |
| 抽样的可复现性 | 同种子 / 换种子 / 等分候选 |
| usage 投影与命中率算术 | 夹具数字过 `projectProviderUsage` |
| 生产缓存命中率 | 两台真实运行实例的 `life_events` 聚合，按 DSH 自己的公式分组统计（只读数字，不读正文） |
| token 估算比例 | 四段中文过 `estimateTokens` |

| **没测** | 原因 |
|---|---|
| 真实模型的输出质量、压缩质量 | 不调生成模型，压缩只测常量与校验 |
| 严格意义的缓存命中率 | 生产库只落了累计缓存读，没有成对 hit/miss 字段（见 7.2） |
| 真实账单 | 只看到 usage 的上报值，没对账 |
| 并发、长跑、崩溃恢复 | 单进程跑一次，不覆盖长期运行 |
| 语义质量的人工评测 | 28 个问题是我自己造的，标准答案是我自己标的 |

## 2. 环境与方法

| 项 | 值 |
|---|---|
| Node | `v24.22.1` |
| 依赖 | 0 个 npm 包（只用 `node:sqlite` 与内置模块） |
| 数据库 | 系统临时目录里的真实 SQLite 文件，跑完即删 |
| 语料 | 14 条合成记忆，每条 1–2 句 |
| 问题 | 28 个，两组各 14：A 组复用目标原话里的词，B 组刻意换说法 |
| 召回配置 | `mode: 'semantic'`（默认）、`perRoute: 20`、`limit: 20` |
| 判定 | 目标是否出现在候选里，以及排第几；没出现记「未召回」 |

A 组用原话词，是为了测**字面重合**下这套编码器能不能命中；B 组换说法，是为了测它**在零重合时会怎样**。两组都不是自然语料，数字只对这套语料成立。

## 3. 记忆召回质量

### 3.1 维度扫描

`createHashEncoder()` 默认 64 维。同样的语料与问题，只改维度：

| dim | A 组问题 | 命中@1 | 命中@3 | MRR | 未召回 | B 组问题 | B 组命中@1 | B 组未召回 | B 组误召 |
|---|---|---|---|---|---|---|---|---|---|
| 64（默认） | 21 | **16** | 18 | 0.811 | 2 | 7 | 0 | 6 | 1 |
| 256 | 21 | 17 | 20 | 0.865 | 1 | 7 | 0 | 7 | 0 |
| 1024 | 21 | **19** | 21 | 0.952 | 0 | 7 | 0 | 7 | 0 |
| 4096 | 21 | **20** | 21 | 0.976 | 0 | 7 | 0 | 7 | 0 |

（表里的分组不是按问题集分的，而是按「与目标是否共享词条」重新统计：28 个问题里 21 个至少共享一个词条、7 个零共享。那 21 里包含 B 组 14 条中的 7 条——它们换了说法，但仍保留了原话里的某个词。）

### 3.2 默认 64 维漏在哪里：两个案例

64 维下 A 组有 2 条完全没召回。查桶之后原因是**哈希碰撞把唯一的匹配词抵消了**，不是编码器「不懂语义」：

| 案例 | query 桶 | 目标桶 | 净结果 |
|---|---|---|---|
| m01「路灯什么时候能修好」 | 35: `路灯`(+) ；58: `灯什`(−) | 35: `路灯`(+) ；58: `物业`(+) | +1 −1 = **0**，被 `score > 0` 过滤 |
| m09「那台洗衣服的机器底下积水」 | `洗衣`(+) ；`器底`(+) | `洗衣`(+) ；`水管`(−) | +1 +1 −1 … 归零，dim 64 与 256 都是 0 |

同一个 m09 问题在 1024 维下碰撞消失，目标分数 0.0836、排第 1。

所以默认 64 维的召回损失里，**至少这两条是桶碰撞造成的**，加大维度就能救回来（3.1 的表就是证据）。

### 3.3 换说法（B 组）的表现

7 条零共同词的问题，命中@1 是 **0/7**，dim ≥ 256 时连候选都不再出现。这是这套编码器的设计边界：它做的是字面重合，不是语义。

### 3.4 真实向量：Qwen3-Embedding-8B（4096 维）

同一套语料、同一批问题，换成我们实际在用的模型：`Qwen/Qwen3-Embedding-8B`，4096 维。参考部署是自己托管这一个模型，这里调用的是 SiliconFlow 的同名托管版本（模型相同、主机不同），所以向量维度一致、口径可比。

| 指标 | 值 |
|---|---|
| 向量维度 | 4096 |
| 有共同词问题 | 21 |
| 命中@1 | **21 / 21** |
| 命中@3 | 21 / 21 |
| MRR | **1.000** |
| 未召回 | 0 |
| 零共同词问题 | 7 |
| 零共同词命中@1 | **7 / 7** |
| 零共同词误召 | 0 |
| embedding 调用数 | 2（14 条记忆一次、28 个问题一次） |
| 上报 prompt_tokens 合计 | 354 |

## 5. 五因子打分与权重标定

用仓库真实的 `DEFAULT_WEIGHTS`（importance 0.771、activation 0.05、relevance 2.023、association 0.27、openLoop 1.079、inhibition 0.27）跑四个场景：

| 场景 | importance | activation | relevance | association | openLoop | inhibition | 合计 |
|---|---|---|---|---|---|---|---|
| 默认最小 | 0.534 | -0.200 | 0 | 0 | 0 | 0 | 0.334 |
| 默认中等 | 1.069 | 0 | 1.012 | 0.089 | 0 | 0 | 2.169 |
| 默认最大 | 1.381 | 0 | 2.023 | 0.270 | 1.079 | 0 | 4.753 |
| 刚看过（抑制） | 1.381 | 0 | 2.023 | 0.270 | 1.079 | -0.270 | 4.483 |

| 标定读数 | 值 |
|---|---|
| importance 1 → 5 的增量 | 0.847 |
| relevance 0 → 1 的增量 | 2.023 |
| importance 上限 ÷ relevance 上限 | 44.7% |
| openLoop 的贡献 | 1.079 |
| 压过 openLoop 所需的最低 relevance | 0.533 |
| inhibition 抵消 openLoop 的比例 | 25% |
| activation 触底（-4）的贡献 | -0.200 |
| relevance 单调性 | 通过（4 个候选严格递减） |

三句话读这张表：relevance 是主导项；「这件事没做完」一次能顶 0.533 的相关度；「刚看过」只能压掉未完成的四分之一，压不住真正相关的记忆。importance 走的是 `log1p`，5 倍重要只值 0.847 分——它是一道背景色，不是开关。

| 检查 | 结果 |
|---|---|
| 同种子两次抽样 | `b,a,c` / `b,a,c` → 相同 |
| 换种子 7 | `a,b,d` |
| 不放回 | 是（3 个互不相同） |

| 排序随分数递减 | 是（2.690 → 1.384） |

同种子可复现，意味着「为什么这次想起的是这几条」在本地是能重放的。

## 7. 缓存命中：夹具与生产实测

### 7.1 投影正确性（夹具数字）

| 输入字段 | 投影后 |
|---|---|
| `prompt_tokens` / `completion_tokens` / `total_tokens` | 保留 |
| `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` | 保留 |
| `unknown_key`、`nested` | 丢弃 |

| 指标 | 值 |
|---|---|
| 命中 / 未命中 | 900 / 300 |
| 命中率 `hit/(hit+miss)` | 0.75 |
| 命中占 `prompt_tokens` | 0.75 |
| 传 `null` / 传数组 | 都返回 `null` |

**这一节是夹具数字**：900 和 300 是脚本自己编的，用来验证两件事——只投影白名单计数（厂商的扩展字段、嵌套对象一律丢掉），以及命中率的算术。它**不代表**任何真实请求的缓存命中率。

### 7.2 生产实测：用 DSH 自己的算法，并且把「窗口未滚动」和「窗口刚重建」分开

先说算法。命中率有好几种算法，口径不同结果能差十倍，所以这一节不自己发明公式，直接用 DSH 客户端的两个：

| 口径 | DSH 的公式 | 用在哪 |
|---|---|---|
| **单轮** | `cacheReadTokens ÷ (totalTokens − outputTokens)`，1 位小数 | 每轮用量弹窗（`TurnUsagePanel`） |
| **会话** | `cacheReadTokens ÷ (uncachedInputTokens + cacheReadTokens + cacheWriteTokens)` | 会话用量胶囊（`billedInputTokens(usage)`） |

下面按单轮公式逐轮算，再分组——**分组是这个指标的关键**：前缀缓存在窗口重建的那一刻就作废，之后的第一次请求几乎全是 miss，几轮之后才回到 ~100%。把这两类混在一起平均，得到的数字既不代表稳态、也不代表代价。

| 项 | 实例 A | 实例 B |
|---|---|---|
| 带 usage 的轮次 | 1663 | 307 |
| 时间跨度 | 2026-10-29 → 11-02 | 2026-11-01 → 11-02 |
| 连续段数（= 窗口重建次数） | 26（重建 25 次） | 7（重建 6 次） |
| 平均每段轮数 | ≈ 64 | ≈ 44 |
| **窗口未滚动**：命中率中位 | **99.87%** | **99.78%** |
| 未滚动：p10 | 99.45% | 98.57% |
| 未滚动：低于 90% 的轮数 | 2 / 1620 | 0 / 300 |
| **窗口刚重建**：第一轮命中率中位 | **0.75%** | **2.89%** |
| 全部轮（不分组）中位 | 99.86% | 99.78% |
| 会话口径（各段末轮） | 95.2% – 99.7% | 96.7% – 99.9% |

三句话读这张表：

1. **稳态命中率是 99.8% 量级**：窗口没重建时，1637 轮里只有 2 轮低于 90%（实例 A），实例 B 是 300 轮里 0 轮。这和我们之前实测「90% 以上」是一致的。
2. **重建一次就要全量重发一次 prompt**：段首轮命中率只有 0.75% / 2.89%，那 26 轮和 7 轮是纯粹的额外开销；摊到全部轮次里，它把中位数从 99.87% 压到 99.86%，几乎看不出来。
3. **重建不等于 roll**：`life_rolls` 表里只有 1 条 roll 记录，但连续段有 26 个——重建主要发生在对话/上下文被重置的时候（计数器归零、前缀作废），不是那条 roll 干的。所以在这份数据里，「滚动后 vs 未滚动」表现为「段首 vs 段内」。

字段说明：生产库里这一层存的是宿主投影后的 `{ inputTokens, outputTokens, totalTokens, cacheReadTokens }`，没有 `cacheWriteTokens`，所以会话口径只能用 `cacheReadTokens ÷ (cacheReadTokens + inputTokens)` 近似，上表给的是区间。

## 9. 怎么复现

```bash
node tests/report.mjs
```

- 脚本零依赖、零网络：建临时 SQLite、写 14 个包、跑 4 个维度、算打分与投影，最后删临时库。
- 3.4 / 3.5 那两节要额外给一个 key，脚本才跑：`LIFE_REPORT_EMBED_API_KEY=… node tests/report.mjs --remote`（可选 `LIFE_REPORT_EMBED_ENDPOINT` / `LIFE_REPORT_EMBED_MODEL`）。没给 key 就跳过，其余照跑。key 只从环境变量读，不落盘、不打印。
- 7.2 的生产数字不在这份脚本里：那是从运行中的实例库里聚合出来的（只读 `meta_json.usage` 的计数，按 DSH 的 `cacheReadTokens ÷ (totalTokens − outputTokens)` 逐轮算，再按连续段分组），换一台机器就要重新聚合。
- 语料和问题写死在脚本里。改语料就要重跑、并把本文档的数字一起改——**数字跟着脚本走，不跟着文档走**。
- 输出就是本文档的表格（Markdown 行），可以直接贴回来比对。连续跑两次，输出文件的 SHA-256 完全一致（`7B96FB27…784B1CEB1`），说明这些数字是确定的、不是抽出来的。

## 10. 这套数字证明不了什么

| 想说的 | 目前能说到几分 |
|---|---|
| 「召回准」 | 可以说：真实 4096 维模型在这 28 个问题上 21/21 命中@1、7/7 零共同词也命中。**仍然不能说"生产召回质量"**——28 条问题是我自己造的，规模太小，而且真实记忆流不像这样一问一包 |
| 「hash 编码器能用」 | 可以说：字面重合时 64 维 16/21、1024 维 19/21，零共同词全不中。它是可用的兜底，不是替代品 |
| 「打分合理」 | 只能说：权重比例、单调性、确定性符合设计意图。**不能说符合人的直觉**——没有人工标注对照 |
| 「缓存命中高」 | 可以说：窗口没重建时中位命中率 99.87% / 99.78%（p10 99.45% / 98.57%），重建后的第一轮只有 0.75% / 2.89%。**不能说「永远 99%」**——每重建一次就要全量重发一次 |
| 「token 估得准」 | 只能说：这四段中文 0.656。**不能替代供应商计数** |

要让这些说法再进一步，需要的是：把 28 个问题扩成有人工标注的评测集、让宿主把成对 hit/miss 落库、拿真实账单对一次账。这三件事仓库都还没做，也不假装做了。
